ABSTRACT
This project develops a web-based patient registration, vital-sign recording, five-level triage decision-support, queue management, and IoT telemetry system. The application uses Django with PostgreSQL in deployment and SQLite for development. A Random Forest model combines numeric clinical variables with TF–IDF symptom text and recommends RED, PINK, YELLOW, GREEN, or WHITE; a nurse must confirm or override the recommendation. On a 254-record holdout set, the model achieved 61.42% accuracy, 53.29% balanced accuracy, and 47% macro F1. Three-fold cross-validation on 1,267 records achieved 66.22% accuracy, 59.56% balanced accuracy, 56.93% macro F1, 72.22% route accuracy, and 94.79% within-one-level accuracy. The targeted deployment suite passed 53 of 53 checks. The complete 68-test Django suite passed 53 tests and produced 15 errors caused by a missing staticfiles manifest entry for css/app.css, so the full suite is not reported as passing. No verified evidence is available for physical hardware models, calibration, network performance, or device trials; therefore, IoT findings are limited to the server API, simulator, and automated tests.
Keywords: patient queue management, triage, artificial intelligence, Random Forest, Internet of Things

1.1 ความเป็นมาและความสำคัญของปัญหา
การให้บริการผู้ป่วยนอกต้องเชื่อมโยงข้อมูลตั้งแต่การลงทะเบียน การวัดสัญญาณชีพ การคัดแยกความเร่งด่วน การเรียกคิว ไปจนถึงการติดตามอาการระหว่างรอ หากข้อมูลกระจายอยู่หลายจุด บุคลากรอาจมองเห็นสถานะล่าสุดได้ไม่ครบถ้วนและจัดลำดับผู้ป่วยได้ยาก งานทบทวนด้านการคัดแยกชี้ว่ากระบวนการ triage และการจัดลำดับงานมีผลต่อการไหลของผู้ป่วยและเวลารอ (Oredsson et al., 2011; Corkery et al., 2021)
แนวคิดการคัดแยก 5 ระดับช่วยแบ่งความเร่งด่วนอย่างเป็นระบบ แต่ผลคัดแยกยังขึ้นกับข้อมูล อาการ บริบท และดุลยพินิจของบุคลากร ระบบเรียนรู้ของเครื่องจึงควรทำหน้าที่สนับสนุนการตัดสินใจ มิใช่แทนการวินิจฉัยหรืออำนาจตัดสินใจของพยาบาล (Hong et al., 2018; Raita et al., 2019; World Health Organization, 2021) โครงงานนี้จึงออกแบบให้ผลของ AI แยกจากผลที่พยาบาลยืนยัน และบังคับให้บันทึกเหตุผลเมื่อมีการแก้ไขระดับ
อีกส่วนหนึ่งคือการรับข้อมูลสัญญาณชีพจากอุปกรณ์ผ่าน API เพื่อให้แดชบอร์ดแสดงค่าล่าสุดและสร้างสัญญาณเตือนสำหรับการประเมินซ้ำ แนวคิดการติดตามระยะไกลและ IoT สามารถเพิ่มความต่อเนื่องของข้อมูลได้ แต่ต้องคำนึงถึงความน่าเชื่อถือ ความปลอดภัย และขอบเขตการใช้ข้อมูลสุขภาพ (Islam et al., 2015; Malasinghe et al., 2019; พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562)
1.2 วัตถุประสงค์
เพื่อพัฒนาระบบลงทะเบียนผู้ป่วยและจัดการคิวตามระดับความเร่งด่วน 5 ระดับ
เพื่อพัฒนาแบบจำลอง Random Forest สำหรับเสนอระดับคัดแยกเบื้องต้นจากข้อมูลอาการและสัญญาณชีพ
เพื่อพัฒนากระบวนการให้พยาบาลยืนยันหรือแก้ไขผล AI โดยคงผู้รับผิดชอบการตัดสินใจไว้ที่บุคลากร
เพื่อพัฒนา API รับข้อมูลสัญญาณชีพและแดชบอร์ดสำหรับติดตามผู้ป่วยที่รอรับบริการ

2.1 การคัดแยกผู้ป่วย 5 ระดับ
ระบบคัดแยก 5 ระดับมีจุดมุ่งหมายเพื่อแยกผู้ป่วยที่ต้องช่วยชีวิตทันทีออกจากผู้ป่วยที่สามารถรอได้ โดยอาศัยภาพรวมของอาการ สัญญาณชีพ ความเสี่ยง และทรัพยากรที่คาดว่าจะใช้ คู่มือ Emergency Severity Index อธิบายโครงสร้างการตัดสินใจแบบหลายระดับ ขณะที่งานวิจัย KTAS แสดงความสำคัญของความสอดคล้องและความถูกต้องของผู้ประเมิน (Gilboy et al., 2011; Kwon et al., 2019; Choi et al., 2019)
โครงงานใช้ชื่อสี RED, PINK, YELLOW, GREEN และ WHITE เป็นชั้นผลลัพธ์ และใช้กฎป้องกันความเสี่ยงร่วมกับผลแบบจำลอง การกำหนดสีในซอฟต์แวร์เป็นการปรับใช้เพื่อการศึกษา ไม่ควรนำเกณฑ์ค่าเดียวไปตีความเป็นคำวินิจฉัย
2.2 Random Forest และข้อมูลไม่สมดุล
Random Forest เป็นวิธีรวมต้นไม้ตัดสินใจจำนวนมากโดยสุ่มตัวอย่างข้อมูลและคุณลักษณะ ช่วยลดความแปรปรวนและรองรับความสัมพันธ์ไม่เชิงเส้น (Breiman, 2001) อย่างไรก็ตามข้อมูลคัดแยกมักไม่สมดุล โดยเฉพาะชั้นวิกฤตที่มีจำนวนน้อย จึงต้องพิจารณาค่าความถูกต้องสมดุล ค่าเฉลี่ยแบบ macro และผลรายชั้นควบคู่กับ accuracy (He & Garcia, 2009)
2.3 การแทนข้อความด้วย TF–IDF
ข้อความอาการสำคัญถูกแปลงเป็นเวกเตอร์ด้วย TF–IDF ซึ่งให้น้ำหนักคำตามความถี่ในเอกสารและความหายากเมื่อเทียบกับชุดเอกสารทั้งหมด โครงงานใช้ทั้ง unigram และ bigram เพื่อรักษาข้อมูลวลีบางส่วน (Salton & Buckley, 1988)
2.4 การป้องกันข้อมูลรั่วไหล
ข้อมูลรั่วไหลเกิดเมื่อคุณลักษณะฝึกมีสารสนเทศที่เกิดหลังผลลัพธ์หรือสัมพันธ์โดยตรงกับฉลาก ทำให้ตัวชี้วัดสูงเกินจริง (Kaufman et al., 2012) โครงงานจึงตัด KTAS_expert, KTAS_RN, Error_group, mistriage, Diagnosis in ED, Disposition, Length of stay_min และ KTAS duration_min ออกจากคุณลักษณะ
2.5 ระบบติดตามสัญญาณชีพและ IoT
สถาปัตยกรรม IoT ด้านสุขภาพเชื่อมอุปกรณ์ เครือข่าย บริการประมวลผล และส่วนแสดงผล การใช้จริงต้องตรวจสอบความถูกต้องของเซนเซอร์ ความต่อเนื่องของการส่งข้อมูล การยืนยันตัวตน และการจัดการเหตุขัดข้อง (Islam et al., 2015; Malasinghe et al., 2019) ในโครงงานนี้จึงจำกัดข้อสรุปเฉพาะ API และโปรแกรมจำลองจนกว่าจะมีหลักฐานอุปกรณ์จริง
2.6 เทคโนโลยีเว็บและฐานข้อมูล
Django ใช้แนวคิด model–template–view ร่วมกับระบบ URL routing, authentication, ORM และ testing framework (Django Software Foundation, 2026) โครงงานใช้ PostgreSQL ในการนำขึ้นใช้งาน และใช้ SQLite เป็นทางเลือกสำหรับการพัฒนาภายในเครื่อง

บทที่ 5

5.1 สรุปผล
โครงงานได้ต้นแบบเว็บที่เชื่อมการลงทะเบียน สัญญาณชีพ AI ช่วยคัดแยก การยืนยันโดยพยาบาล การจัดลำดับคิว และ telemetry เข้าด้วยกัน ระบบรองรับ 5 ระดับและกำหนดเส้นทาง RED/PINK ไปฉุกเฉิน YELLOW ไปสังเกตอาการได้ และ GREEN/WHITE เข้าคิว OPD ผลประเมินยืนยันว่าระบบทำงานตามชุดทดสอบเฉพาะ 53 รายการ แต่แบบจำลองยังไม่ถึงเป้าหมาย accuracy ร้อยละ 75 และชุดทดสอบทั้งหมดติดข้อผิดพลาด staticfiles 15 รายการ
5.2 อภิปรายผล
ความไม่สมดุลของชั้นข้อมูลสัมพันธ์กับผลรายชั้น โดย RED และ WHITE มีตัวอย่างน้อยกว่า GREEN และ YELLOW อย่างชัดเจน ผล holdout ของ RED มี recall .80 แต่ support เพียง 5 จึงมีความไม่แน่นอนสูง ส่วน WHITE มี recall .07 แสดงความเสี่ยงต่อการทำนายเป็นชั้นที่เร่งด่วนกว่า การรายงาน balanced accuracy และ macro F1 จึงเหมาะกว่าการพิจารณา accuracy ค่าเดียว ซึ่งสอดคล้องกับข้อเสนอด้านการเรียนรู้จากข้อมูลไม่สมดุล (He & Garcia, 2009)
การคงพยาบาลไว้ในวงจรตัดสินใจช่วยลดความเสี่ยงจากข้อผิดพลาดของแบบจำลอง และสอดคล้องกับหลักการกำกับดูแล AI สุขภาพ (World Health Organization, 2021) อย่างไรก็ดี กระบวนการนี้จะประเมินได้ครบถ้วนเมื่อมีข้อมูลการยืนยันและการ override จากการใช้งานจริง ซึ่งหลักฐานปัจจุบันยังมีจำนวนศูนย์แถว
5.3 ข้อจำกัด
ข้อมูลมี 1,267 ระเบียนและมีความไม่สมดุล โดย RED มี 26 และ WHITE มี 75 ระเบียน
ไม่มีข้อมูลพยาบาลยืนยันจากระบบจริงสำหรับฝึกหรือประเมินเพิ่มเติม
ไม่มีตัวชี้วัดราย fold จึงยังประเมินความแปรปรวนของ cross-validation ไม่ได้
full Django test suite ยัง fail จาก staticfiles manifest
ยังไม่มีหลักฐานรุ่นอุปกรณ์ เฟิร์มแวร์ การสอบเทียบ การทดลองฮาร์ดแวร์จริง ความหน่วง และ packet loss
ระบบเป็นต้นแบบเพื่อการศึกษา ไม่ผ่านการรับรองสำหรับตัดสินใจทางคลินิก
5.4 ข้อเสนอแนะ
แก้ staticfiles manifest และรันชุดทดสอบทั้งหมดให้ผ่าน 68/68 พร้อมเก็บ log เวอร์ชันสุดท้าย
บันทึกผลราย fold ค่าเฉลี่ย ส่วนเบี่ยงเบนมาตรฐาน และช่วงความเชื่อมั่น
